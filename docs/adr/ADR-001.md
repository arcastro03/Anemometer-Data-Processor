# ADR-001: Use CSV Files as the Primary Input to the Wind Data Processing Application

## Status

Accepted

## Context

The purpose of this application is to process wind measurement data collected from pressure transducer sensors. The sensors measure differential pressure, which can be converted into wind velocity. The application will then calculate useful results such as average wind speed, turbulence intensity, and plots of the measured data.

I needed to decide how the application should receive sensor data. One option was to connect the application directly to the Raspberry Pi Pico and collect sensor measurements in real time. Another option was to separate data collection from data analysis and have the application read previously recorded CSV files.

Most of my existing experimental data is already stored in CSV files, and I want to be able to repeatedly analyze the same datasets while developing and testing the application. Direct communication with the sensors would also require the application to handle hardware communication, sampling timing, device connection problems, and data processing at the same time.

Because the main purpose of this application is data analysis rather than sensor control, separating acquisition from processing keeps the application focused on one responsibility.

## Decision

The application will use CSV files as its primary input format.

Sensor acquisition will remain separate from the analysis application. The Raspberry Pi Pico or another data acquisition program will collect measurements and save them to a CSV file. The application will then load that CSV file, validate its contents, convert the pressure measurements into wind velocity when necessary, calculate statistics, and generate plots and other results.

The internal processing code should also be separated from the CSV-loading code so that another input source could be added later without rewriting the calculations.

## Alternatives Considered

### 1. Read data directly from the Raspberry Pi Pico

The application could communicate with the Pico over USB serial and process measurements as they arrive.

This would allow live wind-speed displays and real-time calculations. I did not choose this approach because it would tightly couple the analysis software to the sensor hardware. Testing the application would require either having the Pico connected or creating simulated serial data. The program would also need to manage serial communication, connection failures, sampling timing, and data processing simultaneously.

This may still be useful as a future feature, but it adds complexity that is not necessary for the current purpose of the application.

### 2. Store the measurements in a database

Another option was to import sensor measurements into a database such as SQLite and have the application query the database.

A database could make it easier to manage a large number of experiments and attach metadata to individual tests. However, the current datasets are relatively simple files, and CSV is already the format produced by the existing experimental workflow.

Using a database now would require an additional import and storage layer without providing enough benefit for the current scope of the project.

## Consequences

### Positive consequences

Using CSV files makes the application easier to develop and test because the same experimental dataset can be processed repeatedly without running the sensors again.

It also separates data acquisition from data analysis. Problems with the Raspberry Pi Pico, sensor wiring, or serial communication will not prevent previously collected data from being analyzed.

CSV files are also portable and can be opened by other programs such as Excel, MATLAB, or Python, which makes it easier to verify the application's results.

### Negative consequences

The application will not initially be able to display or analyze sensor measurements in real time. A separate data acquisition process must collect the measurements and create the CSV file before the application can analyze them.

The application must also define and enforce an expected CSV structure. Files with missing columns, different column names, incorrect units, or malformed data will require validation or conversion before they can be processed.

Choosing CSV as the initial boundary also means that adding live sensor input later will require creating another input adapter and deciding how real-time samples should be represented inside the application.

Finally, very large datasets may eventually become less convenient to manage as individual CSV files than they would be in a database. If the project grows to include many experiments, searchable metadata, or long-term data storage, the storage architecture may need to be reconsidered.
